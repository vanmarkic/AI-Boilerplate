### IMPORTANT Issues (2)

**File:** `apps/tfc/backend/engine/exercise_engine.py:327–340`
**Issue:** `_apply_system_effects` uses `.get()` on a TypedDict, but `DecisionOptionSnapshot` is a TypedDict, not a plain dict. At runtime in CPython TypedDicts are plain dicts, so `.get()` works, but it circumvents the static type system. The declared type of `selected_options` is `list[DecisionOptionSnapshot]`, and mypy/pyright will flag `opt.get("system_effects", [])` as an error on TypedDict instances because TypedDict does not define `.get()` returning a default. The field `system_effects` is non-optional on the TypedDict (no `total=False`), so direct key access is both correct and type-safe.

Replace:
```python
for fx in opt.get("system_effects", []):
    if fx.get("power_state") is not None:
        ...
    if fx.get("operational_state") is not None:
        ...
```
With:
```python
for fx in opt["system_effects"]:
    if fx["power_state"] is not None:
        ...
    if fx["operational_state"] is not None:
        ...
```
The `.get()` fallback to `[]` is also a silent swallower of any future structural mismatch — if `system_effects` is missing for some reason, failing loudly is preferable.

**File:** `apps/tfc/backend/features/exercise/engine_decision_service.py:71–73`
**Issue:** System effects are silently skipped on the player-close path. The TODO comment is clear and the separation is deliberate, but there is no test asserting that effects are *not* applied on this path, and no documentation of what a player-close call actually produces in terms of system state. If a scenario author sets `system_effects` on an option and a player closes the decision normally (not via timeout), they will see zero system state changes with no error and no diagnostic. This is a behavioral gap that will surface as a confusing bug during scenario authoring.

Suggestion: Add a test in `engine_decision_service` that closes a decision with an option that has `system_effects` and asserts that no `system_state_change` is broadcast yet — making the incomplete path explicit and regression-safe before Phase 4 fills it in.

### Suggestions (3)

**File:** `apps/tfc/backend/features/scenario/scenario_content.py:17–19`
**Observation:** `SystemEffectDef.operational_state` accepts any `str | None`, but `SystemManager.set_operational` only accepts `"green"`, `"yellow"`, or `"red"` (validated against `OPERATIONAL_ORDER`). An invalid value like `"degraded"` passes Pydantic validation, reaches `_apply_system_effects`, calls `set_operational`, and is silently discarded (because `state not in OPERATIONAL_ORDER` returns `None`). The failure is invisible — no error, no log, no state change.

The fix is a `Literal["green", "yellow", "red"] | None` type on both `SystemEffectDef.operational_state` and the corresponding `SystemEffect` TypedDict field. This pushes validation to the schema boundary where it belongs and eliminates the silent no-op path. The same applies to `SystemStateDef.operational_state` in the same file, which has the same issue but predates this diff.

**File:** `apps/tfc/backend/features/scenario/scenario_content.py:30`

Add `max_plays: int = Field(default=1, ge=1)` now, before enforcement is built on top of it.
