What Quality Means In TFC
For this project, I used a stricter bar than normal CRUD-app quality. In TFC, quality means:

Simulation invariants hold across every entry path.
Scheduled tick, timeout, GM-trigger, player-close, and forced-card flows must converge on the same engine truth.

Engine state is the single source of truth.
Phase, turn, score tier, systems, and decision lifecycle must be consistent from backend engine to WS messages to frontend store.

Behavior is path-independent.
A feature like system degradation or completion cannot work only on the happy path and fail on timeout or manual trigger.

The engine remains pure and deterministic.
Feature routers and services can orchestrate, but they should not rely on scattered private-engine behavior in ways that create hidden alternate flows.

Tests cover the real state machine, not only isolated functions.
In TFC, the highest-value tests are cross-path state transition tests: close vs timeout, scheduled vs force-triggered, completed vs stopped.

Player UX correctness matters as much as backend correctness.
If the engine completes but the player never sees completed, that is still low quality. The completion overlay work is directionally right because it treats UX as a contract, not decoration.

Specs and implementation must stay aligned.
This branch did good work here overall: the scoring and systems changes were documented, and most of the design decisions were explicit.
