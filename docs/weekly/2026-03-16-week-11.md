### Why these decisions
- **`@hey-api/client-angular` over `client-fetch`**: using Angular's `HttpClient` gives us interceptors (for JWT injection), SSR compatibility, and testability with `HttpClientTestingModule` — all free. The generic fetch client would have needed manual wrappers for each of these.
- **`ui-` selector prefix**: the `app-` prefix is Angular's default and creates ambiguity between application components and library components. `ui-` makes it instantly clear a component comes from the shared library. This also aligns with the AGENTS.md convention.
- **Python package extraction**: isolated packages enable independent versioning and testing, and prevent circular imports between feature modules.

## 3. Map Components & Storybook (Mar 12–13)

### What was done
- Built a full MapLibre component suite (`MapViewComponent`, tooltip, popup, drawer panel).
- Integrated Protomaps for self-hosted vector tiles with a design-token-driven style builder.
- Generated static `style.json` from design tokens at build time.
- Added an "ocean" color theme extracted from UI reference screenshots.
- Added a theme switcher toolbar to Storybook.
- Fixed multiple Storybook/map rendering issues: CSS cascade conflicts (`@layer vendor`), MapLibre canvas positioning, OKLCH→hex color conversion, `previewHead` CSS injection.

### Why these decisions
- **Protomaps over commercial tile providers**: self-hosted PMTiles means no API keys, no rate limits, no vendor lock-in, and offline-capable deployments. The single-file archive format is simpler to deploy than a full tile server.
- **Static `style.json` generation**: generating the MapLibre style at build time from design tokens ensures map colors always stay in sync with the design system. Runtime generation would add startup latency and be harder to cache.
- **OKLCH→hex conversion**: MapLibre GL JS does not support OKLCH color syntax. Converting at the style-builder level keeps the source-of-truth in OKLCH tokens while producing compatible output.
- **`@layer vendor` for third-party CSS**: MapLibre's stylesheet was overriding design-system tokens due to cascade specificity. Wrapping it in a low-priority CSS layer solved the conflict without `!important` hacks.

- Fixed e2e test: added Keycloak init timeout to prevent CI blocking, regex-matched `<br>` in h1 text.
- Ran full AGENTS.md compliance scan; fixed all violations (oversized files split, hardcoded CSS replaced with tokens).
- Installed and configured Ruff linter for Python; fixed all linting errors.
- Made Docker base images configurable via `docker-compose` build args (then reverted to daemon-level config after evaluating trade-offs).
- Replaced `window.__ENV__` with Angular `fileReplacements` for environment config.
- Removed redundant GitHub Actions checks to speed up CI.

### Why these decisions
- **Vitest 4 `projects` over deprecated `workspace.ts`**: Vitest 4 removed the workspace file in favor of `projects` in the root config. Staying on the deprecated format would break on the next minor bump.
- **Ruff over flake8/pylint**: Ruff is 10-100x faster, replaces multiple tools (flake8, isort, pyupgrade), and has first-class `pyproject.toml` support. No reason to keep slower alternatives.
- **`fileReplacements` over `window.__ENV__`**: Angular's built-in environment files are type-safe, tree-shakeable, and don't require runtime DOM access. The `window.__ENV__` pattern was a workaround for Docker deployments we don't need yet.
- **Docker image ARGs reverted**: making every base image a build arg added complexity to `docker-compose.yml` for a problem better solved at the Docker daemon level (registry mirrors). Keeping things simple won.

## 6. Real-Time & API Exploration (Mar 16)

### What was done
- Built a generic SSE (Server-Sent Events) broadcast system powered by PostgreSQL `LISTEN/NOTIFY`, with backend (`SseBroadcaster`) and frontend (`SseService`) integration (PR #76).
- Added SSE channel names to the OpenAPI spec for typed TypeScript client generation.
- Documented intentional auth deferral on the SSE endpoint.
- Evaluated PostgREST as a potential API layer (documented in `docs/postgrest-api-evaluation.md`).
- Fixed all tests to pass — 24 backend + 13 frontend green.

### Why these decisions
- **PostgreSQL LISTEN/NOTIFY as the event bus**: instead of adding a dedicated message broker (Redis Pub/Sub, RabbitMQ), we leverage PostgreSQL's built-in `LISTEN/NOTIFY` mechanism. Since Postgres is already in the stack, this adds zero infrastructure. The broadcaster listens on a PG channel and fans out notifications to all connected SSE clients.
- **SSE over WebSockets**: SSE is simpler (HTTP/1.1 compatible, auto-reconnect, no upgrade handshake), works through all proxies/load balancers, and is sufficient for server→client push. WebSockets would only be needed if we required bidirectional communication, which we don't currently.
- **Auth deferral on SSE**: SSE connections via `EventSource` cannot send custom headers. Implementing auth requires either cookie-based tokens or a query-param token handshake. This was intentionally deferred and documented rather than implemented incorrectly.
- **PostgREST evaluation (not adoption)**: PostgREST could eliminate boilerplate CRUD endpoints, but it bypasses our Pydantic validation layer and Keycloak auth middleware. The evaluation doc captures trade-offs for a future decision.

### How hard would it be to replace or complement SSE with WebSockets?

**Short answer: complementing is straightforward (moderate effort); full replacement is possible but brings unnecessary complexity for our current needs.**

#### What would change — backend

| Layer | Current (SSE) | WebSocket equivalent | Effort |
|---|---|---|---|
| **Transport** | `StreamingResponse` with `text/event-stream` in `sse_router.py` | FastAPI `WebSocket` endpoint with accept/receive/send loop | **Low** — FastAPI has first-class WebSocket support |
| **EventBus core** (`core/sse.py`) | `asyncio.Queue`-based fan-out from PG LISTEN/NOTIFY | **No change** — the EventBus is transport-agnostic; subscribers already consume from queues | **None** |
| **Broadcast decorator** (`core/broadcast.py`) | Calls `event_bus.publish()` | **No change** — publish side is identical regardless of consumer transport | **None** |
| **Channel registry** (`sse_router.py`) | Allowlist + OpenAPI enum injection | Needs equivalent validation on WS connect; OpenAPI does not natively describe WebSocket channels, so the typed enum generation would need a custom approach | **Medium** |
| **Auth** | Deferred (EventSource can't send headers) | WebSocket handshake **can** send headers or use a token-in-first-message pattern — this actually **solves** the current SSE auth gap | **Medium** (but beneficial) |
| **Proxy / infra** | Works over HTTP/1.1; `X-Accel-Buffering: no` header | Requires `Upgrade: websocket` support in every proxy/LB hop; Nginx needs `proxy_set_header Upgrade` and `proxy_set_header Connection "upgrade"` directives; some corporate proxies and CDNs strip upgrade headers | **Low–Medium** depending on deployment environment |

#### What would change — frontend

| Layer | Current (SSE) | WebSocket equivalent | Effort |
|---|---|---|---|
| **EventSourceService** | Wraps browser `EventSource` API with reconnect + ref-counting | Replace with `WebSocket` wrapper (or use a library like `rxjs/webSocket`); must implement reconnect logic manually since WebSocket has no built-in auto-reconnect | **Medium** |
| **SignalStore integration** (`with-live-events.ts`) | Subscribes to `Observable<T>` from service | **No change** if the new WS service exposes the same `channel<T>(name): Observable<T>` interface | **None** |
| **Type safety** (`SseChannel` type) | Derived from OpenAPI enum | Would need an alternative source (shared const, custom codegen) since OpenAPI has no WebSocket channel spec | **Low** |

#### Effort summary

- **Complement (run both SSE + WS):** ~2–3 days. Add a parallel `ws_router.py` with a `/api/ws/{channel}` endpoint that reads from the same `EventBus` queues. Frontend adds a `WebSocketService` alongside `EventSourceService`. Features opt into whichever transport fits (SSE for simple server-push, WS for bidirectional). The EventBus, broadcast decorator, and SignalStore integration remain untouched.
- **Full replacement (remove SSE, WS only):** ~3–5 days. Same backend/frontend work as above, plus: migrate all existing SSE consumers, remove SSE router, update OpenAPI codegen pipeline, add Nginx/proxy WebSocket upgrade config, and re-test all real-time flows.

#### When WebSockets would be worth it

- **Client→server messaging needed** (chat, collaborative editing, command acknowledgements) — SSE is server→client only.
- **High-frequency bidirectional data** (live cursors, multiplayer state sync) — opening a second HTTP request for client→server messages adds latency vs. a single full-duplex connection.
- **Auth on the real-time channel** — ironically, WebSocket makes auth easier than SSE since the handshake supports custom headers and the first message can carry a token. This would close the current auth deferral.

#### When to stick with SSE

- **Server→client push only** (notifications, feed updates, dashboard live data) — SSE is simpler, auto-reconnects natively, works through more proxies, and the current implementation already handles fan-out and backpressure.
- **No bidirectional requirement on the horizon** — adding WebSocket complexity for one-way push is over-engineering.

**Bottom line:** the architecture was designed well — the `EventBus` is transport-agnostic, so adding WebSocket support is a matter of wiring a new endpoint and frontend service without touching the core pub/sub or broadcast logic. Complementing is the recommended path if bidirectional needs arise; full replacement is unnecessary unless SSE's limitations (no client→server, no header-based auth) become blockers.

## 7. RBAC Middleware (Mar 16) — Latest on master

> **Latest master commit**: `2c3c2ef` — Merge PR #78: "Add database-driven RBAC middleware with permission management"

### What was done
- Added a database-driven RBAC (Role-Based Access Control) system integrated with Keycloak.
- Moved `RolePermission` model and repository into `core/` for cross-feature reuse.
- Added SSE endpoints to the RBAC public allowlist so unauthenticated SSE connections continue to work.
- Fixed test isolation, public route handling, and linting issues post-rebase.

### Why these decisions
- **Database-driven permissions over static role maps**: storing permissions in PostgreSQL allows runtime updates (e.g., an admin can grant/revoke permissions without redeploying). A hardcoded role→permission map would require a code change and deploy for every permission tweak.
- **RBAC in `core/` rather than a feature module**: authorization is cross-cutting — every feature needs it. Placing it in `core/` makes it available to all features without tier-import violations and keeps it alongside the existing `core/auth.py` Keycloak integration.
- **Public allowlist for SSE**: since SSE auth was intentionally deferred (see section 6), the RBAC middleware needs to explicitly skip those routes. This was handled via a configurable allowlist rather than a blanket bypass.
